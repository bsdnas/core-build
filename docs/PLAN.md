# План: живой форк TrueNAS CORE с постоянным трекингом FreeBSD

Статус: 2026-08-02. Решения приняты: имя проекта **bsdnas**, база **stable/15**, старт от dravanet,
хостинг — свой GitHub org, сборка — FreeBSD VM на Proxmox (поднята, см. журнал).
Открыто: имя GitHub org (аккаунт `kamuzon` существует, `bsdnas` свободен).

## Журнал

**2026-08-09 — апгрейд пула: необратимость оказалась мягче, чем я утверждал.**

На обновлённой системе (OpenZFS 2.4.3) выполнен `zpool upgrade tank13`. Пул создан
ещё в 13.3 на OpenZFS 2.2; включились восемь фич, все из 2.3/2.4:
`fast_dedup`, `longname`, `large_microzap`, `raidz_expansion`,
`block_cloning_endian`, `physical_rewrite`, `redaction_list_spill`.

Система после апгрейда: `READY`, пул ONLINE/healthy, шара включена, джейл `up`.

*Проверка обратимости — предметная, а не рассуждением.* Загрузился установщиком
официальной 13.3-U1.2 (OpenZFS 2.2) и выполнил `zpool import`:

```
pool: tank13
state: ONLINE
status: The pool was last accessed by another system.
action: The pool can be imported using its name or numeric identifier and the '-f' flag.
```

**Ни слова про несовместимые фичи — пул импортируется.** Причина видна по
состояниям: все включённые фичи находятся в состоянии `enabled`, активных —
**ноль**. Фича блокирует старую реализацию, только когда становится `active`,
то есть когда её действительно начинают использовать.

*Корректировка сказанного ранее.* Я утверждал, что после `zpool upgrade` возврат
на 13.3 невозможен. Точная формулировка:

* сразу после `zpool upgrade` пул **остаётся импортируемым** старой OpenZFS 2.2,
  пока новые фичи только `enabled`;
* как только любая из них станет `active` — например, при включении дедупликации
  или создании длинных имён — доступ старой системе закроется;
* переход в `active` происходит как побочный эффект обычной работы и никак
  не анонсируется.

Практический вывод для пользователей: `zpool upgrade` — не мгновенная точка
невозврата, но и не безопасная операция. Окно отката существует, оно молчаливо
закрывается, и полагаться на него нельзя. Разумный порядок: обновить систему,
убедиться что всё работает, пожить так — и только потом делать `zpool upgrade`,
уже сознательно расставаясь с возможностью вернуться.

на порядок, консоль нужна только для установщика, где сети ещё нет. **NB:** после

**2026-08-07 — ГЛАВНОЕ: официальная TrueNAS CORE 13.3 обновлена до нашей сборки

Это и есть проверка обещания форка. До сих пор проверялось только обновление
нашей сборки на нашу же (15 → 15, разница в несколько коммитов). Теперь пройден
настоящий путь: живая система на снятой с поддержки 13.3 перенесена на FreeBSD,
который получает обновления безопасности.

Исходная система — **официальный образ iX** `TrueNAS-13.3-U1.2`
(`download-core.sys.truenas.net`, 949 МБ), поставленный автоприёмкой, с реальной
конфигурацией: пул-зеркало `tank13`, датасет `tank13/data`, SMB-шара `legacy13`.

```
13:27:22  до обновления: пулов 1, шар 1
13:40:59  загрузка с диска
13:42:46  система готова (80с)
13:42:47  версия: "TrueNAS-15-MASTER-202608071028"
13:42:48  пулов: 1, шар: 1, шелл root: /usr/local/bin/zsh
13:42:48  конфигурация сохранена: пулов 1, шар 1
13:42:48  ПРИЁМКА ОБНОВЛЕНИЯ ПРОЙДЕНА
```

Проверено предметно: пул `tank13` (создан OpenZFS 2.2, работает на 2.4.3) —
ONLINE, healthy; датасеты `tank13`, `tank13/data`; шара `legacy13` →
`/mnt/tank13/data`, enabled. Всё это заведено ещё в 13.3.

За один шаг сменились: FreeBSD 13.3 → stable/15, OpenZFS 2.2 → 2.4.3,
Samba 4.20 → 4.23, Python в портах 3.9 → 3.11, схема конфигурации — поколение.
Пул намеренно не апгрейдился (`zpool upgrade` необратим): проверялось, что
система поднимется и увидит его в старом формате.

Весь цикл — 15 минут и полностью автоматически.

**Автоприёмка** (`tools/acceptance.sh`) написана и обкатана: режимы `install`,
`upgrade`, `verify`, `snapshot`, `rollback`. Ключевое — `upgrade` снимает число
пулов и шар до обновления и сверяет после; при потере падает с явным сообщением,
а не рапортует об успехе. Именно эта проверка отсутствовала у установщика iX.

Она сразу принесла пользу: поставив эталонную 13.3, показала, что у iX шелл root —
`/usr/local/bin/zsh`, а не `/bin/csh`, к которому я свёл вчерашнюю правку.
Порты во FreeBSD ставятся в `/usr/local`, `shells/zsh` у нас собирается и лежит
именно там — неверен был только путь. Исправлено (`63b5332876`): чиним путь,
а не подменяем оболочку. Вывод на будущее: держать эталонную установку постоянно —
сравнение с оригиналом ловит то, чего не видно изнутри своей сборки.

**Точки возврата стенда:** `configured` (наша сборка + пул + шара) и `core13`
(официальная 13.3 + пул + шара). Возврат — 4 минуты вместо часа переустановки,
за день окупились дважды.

*Мои ошибки в обвязке, обе поучительны для будущей автоматики:* длинную операцию
нельзя запускать под коротким таймаутом — прерванная на середине, она оставляет
стенд в промежуточном состоянии, и следующий запуск падает на непонятном месте;
признак завершения не должен совпадать с собственной командной строкой, иначе
`pgrep` находит сам сторож и ждёт вечно.

**2026-08-04 — ОБНОВЛЕНИЕ РАБОТАЕТ. Первопричина найдена, исправлена, проверена.**

Итог прогона на стенде: система `202608032329` с пулом и SMB-шарой обновлена
образом `202608041953`.

```
версия:    TrueNAS-15-MASTER-202608041953   (было 202608032329)
состояние: READY
пул tank:  ONLINE, healthy
шара:      traceshare -> /mnt/tank/share, enabled
датасеты:  tank, tank/share
шелл root: /bin/csh
пароль:    прежний (API отвечает)
среды:     default, Initial-Install, default-20260804-202447 (активна)
```

**Причина была двойной, и обе части — про переполнение `/tmp` установщика (tmpfs 5 МБ):**

| источник | размер | как попадал в tmpfs |
|---|---|---|
| `/data/pkgdb/freenas-db` | 24 МБ | копировался целиком, удалялся **после** копирования |
| `/boot/modules` | ~93 МБ | сохранялся «на всякий случай» (`openzfs.ko.debug` — 37 МБ, `openzfs-debug.ko.debug` — 41 МБ) |

`cp` обрывался на середине с ENOSPC, результат **не проверялся**, и в новую
загрузочную среду уезжала обрезанная конфигурация — при том что установщик
рапортовал «The installer has preserved your database file». Отсюда пропажа пулов,
шар и пароля после обновления.

Воспроизведено в лоб в шелле установщика:

```
# cp -pR /tmp/o/data/. /tmp/dp
cp: /tmp/o/data/./pkgdb/freenas-db: No space left on device
tmpfs   5.0M   4.9M   116K   98%   /tmp
```

*Исправления:*

* `c8b9504824` — `pkgdb` и `crash` исключаются **до** копирования, каждый элемент
  копируется с проверкой кода возврата, целостность базы сверяется по контрольной сумме;
* `96599d2e87` — модули ядра не сохраняются вовсе. Это и по сути правильно: модуль,
  собранный под прежнюю версию FreeBSD, в новом ядре даёт панику — тот самый класс
  отказа, что наблюдался при попадании 15.0-модуля в ядро 15.1;
* `cd14ebf` (core-build) — tmpfs установщика поднят до 64 МБ как запас (на сам дефект
  не влияет, но убирает хрупкость).

Теперь при нехватке места установка прервётся с внятным сообщением и выводом `df`,
а не потеряет конфигурацию молча.

**Оба дефекта, найденные при проверке обновления, закрыты:** потеря настроек и
неработающий пункт Shell консольного меню (`/usr/bin/zsh` → `/bin/csh`).

**2026-08-04 — найдена вероятная первопричина потери конфигурации: `/tmp` установщика 5 МБ.**

Измерено в шелле установщика:

```
Filesystem      Size  Used  Avail  Capacity  Mounted on
/dev/md0.uzip   624M  486M    88M       85%  /
tmpfs           5.0M  8.0K   5.0M        0%  /tmp
```

А `preserve_data()` копирует в этот пятимегабайтный tmpfs **весь каталог `/data`**
целиком (`cp -pR /tmp/data_old/data/. /tmp/data_preserved`) — и результат копирования
**никак не проверяется**. Для системы, где `/data` подбирается к лимиту (сертификаты,
больше шар и пользователей, дамп в `/data/crash`), `cp` отработает частично и молча,
после чего установщик восстановит в новую среду обрезанную или пустую базу. Это
объясняет исходный симптом без всяких миграций и пакетов.

Подтверждение с другой стороны: моя трассировка (md5 + запрос sqlite3 на каждый вызов)
сама переполнила `/tmp`, и обновления стали падать на `mkdir: /tmp/data: No space left
on device`, а установщик — зацикливаться, не в силах создать даже `/tmp/answer`.

*Что при этом доказано измерением:* когда места хватает, сохранение работает идеально.

```
TRACE 1-old-be:    md5=78cf445e633b048f93f42ea19b5d2742  volumes=1
TRACE 2-preserved: md5=78cf445e633b048f93f42ea19b5d2742  volumes=1
```

**Правка шелла подтверждена на живой системе.** После чистой установки сборки
`202608032329`: `shell root = /bin/csh` (было `/usr/bin/zsh`). Дефект с неработающим
пунктом Shell консольного меню закрыт.

**Что чинить в `preserve_data`:** проверять результат `cp` и падать громко, а не молча;
проверять свободное место до копирования; либо копировать не весь `/data`, а
осмысленный набор (база, сертификаты, ключи), исключая заведомо крупное (`crash`).
Отдельно — увеличить tmpfs установщика: 5 МБ на весь рабочий каталог мало.

**Три ловушки, каждая стоила цикла сборки:**

1. *Пакет установщика не пересобирается.* `freenas-installer-15` — статичная версия
   без ревизии исходников, poudriere считает его вечно актуальным. Правки `install.sh`
   не доезжают до образа, пока пакет не удалить руками. Привязать версию к ревизии
   middleware, как у других портов через `REVISION=`.
2. *Кавычки в кавычках.* `bsdusr_username=\'root\'` внутри одинарных кавычек — sh так
   не умеет, установщик перестал разбираться целиком. `sh -n` ловит мгновенно, но
   спотыкается на дефисах в именах функций (`pre-install()`), которые FreeBSD допускает.
   Нужна обёртка, обходящая расхождение, и прогон по всем `*.sh` и `pkg-*.in` до коммита.
3. *`set -e` в критической секции.* `_vol=$(sqlite3 ...)` возвращает код неудачи
   подстановки — установка прерывалась сразу после установки пакетов. Диагностика
   обязана быть неспособной уронить диагностируемое: каждое присваивание подстраховано,
   выход всегда нулевой.

**Точка возврата вместо переустановки.** Снят снимок Proxmox `configured` (чистая
установка + пул + шара + известный пароль). Откат занимает две минуты против часа
на полный цикл. Для автоприёмки — обязательный элемент.

**2026-08-03 — ПУНКТ 3: база переведена на stable/15, сборка и обновление работают,
найдены два дефекта пути обновления.**

*Перенос базы.* Патч-сет с `releng/15.0` перенесён на `stable/15` rebase-моделью.
Из шести патчей осталось **пять**: `ctld: Return from the inner "main" loop on EINTR`
уже в апстриме (`0efab2ba4c0`), черри-пик оказался пустым. Конфликтовал один патч —
`ctld: change configuration live`: в FreeBSD 15 демон переписан на C++, апстрим
отрефакторил два места. Разрешено осмысленно (версия апстрима + новые вызовы патча),
а не выбором стороны:

```cpp
control_postfork();   pidfile.close();        // вместо conf->close_pidfile()
newconf->shutdown();  control_shutdown();     // вместо ручной подмены конфига
```

Выбросить эти патчи нельзя: в middleware есть `middlewared: live-configure ctld via
control-socket`, без базовой части ломается живая переконфигурация iSCSI.

Ветки в `bsdnas/os`: `base/stable-15` (новая), `base/releng-15.0` (резерв), `bsdnas`
(прежняя). Для push потребовался scope `workflow` у токена — `stable/15` содержит
файлы GitHub Actions.

*Сборка:* 1 ч 36 мин, портов упало 0. Смена базы **не обесценила репозиторий пакетов** —
пересобрались только 10 модульных портов (`realtek-re-kmod`, `open-vm-tools` и т. п.),
501 пакет остался валидным: ABI `FreeBSD:15:amd64` не изменился. Значит регулярный
подъём базы внутри мажорной ветки стоит меньше часа, как и закладывалось.

*Проверка обновлением (не чистой установкой).* На диске была наша сборка
`202608031039` с пулом и SMB-шарой. Выбран `Upgrade Install` → `Install in new boot
environment`. Результат: система загрузилась, `version = TrueNAS-15-MASTER-202608031137`,
`state = READY`, данные целы — пул `tank` (guid 10840638625722336763) найден, импортирован,
датасет `tank/share` на месте.

**Дефект 1: при обновлении теряется конфигурационная база.** После апгрейда
`storage_volume` и `sharing_cifs_share` пусты, пароль root не принимается,
хотя установщик рапортует «The installer has preserved your database file».
`/data/update.failed` отсутствует — миграции отчитались об успехе.

Механизм. Post-upgrade скрипт пакета `base-os` восстанавливает базу так:

```sh
rootfs=$(mount | awk '/ \/ / {print $1}')
lastsnap=$(zfs list -t snapshot -d 1 -H -S creation -o name $rootfs | head -1)
```

* `net.inet.tcp.keepidle` = **7200000 мс = ровно 120 минут**, `keepintvl` 75 с,

проекта dual-inet с двумя аплинками; переключение ISP молча убивает установленные
потоки). Но чинить нужно всё равно на своей стороне, потому что рвать может и любой
внешний миррор.

swap через `md(4)`, вмешательство хоста) не подтвердились: замена swap на раздел не
помогла, на гипервизоре ни OOM-killer, ни задач остановки VM.

Диагноз дал crash-дамп после того, как `dumpon` был применён **к работающему ядру**
(`sysrc` прописывает только на следующую загрузку — из-за этого дампов и не было)
и консоль VM стала писаться в файл на гипервизоре через socat:

```
panic: page fault;  fault virtual address = 0x1e9
current process = zpool
#8  vfs_vector_op_register () at vnode_if.c:4772
#9  linker_file_sysinit
#10 linker_load_file (filename="/boot/modules/openzfs.ko")
#12 kern_kldload
```

Механизм: на стадии кастомизации сборка делает chroot в целевой корень и запускает
там `zpool`. ZFS в ядре хоста загружен не был (корень на UFS), поэтому `zpool`
инициировал автозагрузку модуля — а путь `/boot/modules/openzfs.ko` разрешился внутри
chroot, то есть взялся **свежесобранный модуль под FreeBSD 15.0**. Ядро хоста —
15.1-RELEASE-p2. Несовпадение layout'а vnode op vector между 15.0 и 15.1 → page fault.

Ошибка моя: сборочный хост поднят на 15.1, а дерево dravanet целится в 15.0. В README
iX сказано «build environment must be FreeBSD 13.x» для цели 13.x — я счёл это
устаревшим, тогда как реальное требование там именно **совпадение версий**.

*Обход* (быстрый, применён): загрузить базовый `zfs.ko` на хосте (`kldload zfs` +
`zfs_load="YES"` в `/boot/loader.conf`). Тогда `/dev/zfs` уже существует, и chroot'нутый
`zpool` не пытается ничего подгружать.

*Правильное решение* — одно из двух, выбрать при переходе на свой контур:
поднять сборочный хост на 15.0 под текущую цель, либо (предпочтительно, и это и есть
план) поднять цель на stable/15 и оставить хост на 15.1. Требование «версия хоста =
версия цели» зафиксировать в роли `base-freebsd` и в README.

**Первый патч форка.** `make bootstrap-pkgs` падает: `archivers/pxz` удалён из дерева портов
(многопоточность давно есть в самом `xz -T`). В ветке `bsdnas` репозитория сборки заменено
`XZ = "xz -T0"` в `build/config/env.pyd` и убрана обязательная проверка pxz в
`build/tools/check-host.py`. Это ровно тот класс гнили, который форк и должен вычищать
непрерывно.

**Наблюдатель за апстримом** (2026-08-09) — последний пункт этапа 2. Написан
`tools/watch-upstream.sh`, поставлен на еженедельный cron на сборочной машине,
порядок реакции описан в `docs/MAINTENANCE.md`. Подробности — §4.

Первый же прогон вскрыл три вещи, которые стоит запомнить.

*Лента бюллетеней переехала.* Адрес `advisories.rdf`, на который ссылаются
инструкции и который я взял по памяти, отдаёт 404 — но не пустой ответ, а
страницу-заглушку на 15 КБ. Проверка «ответ непустой» такое пропускает; рабочий
адрес — `https://www.freebsd.org/security/feed.xml`. Урок общий: у наблюдателя
должна быть проверка не на факт ответа, а на разбор ожидаемого содержимого.

*Тег релиза ≠ версия порта.* Релизы OpenZFS помечены `zfs-2.4.3`, а
`PORTVERSION` — `2.4.3`. Сравнение «в лоб» давало вечное «доступно обновление»
на уже собранную версию. Наблюдатель, который всегда кричит, бесполезен ровно
так же, как молчащий.

*Правка, не доехавшая до общего репозитория.* Перевод базы на `base/stable-15`
в `repos.pyd` был сделан прямо на сборочной машине и полтора месяца существовал
только там: сборки шли правильные, а исходники в GitHub описывали другую ветку.
Обнаружилось случайно — наблюдатель прочитал ветку из `repos.pyd` и показал
`bsdnas` вместо `base/stable-15`. Это второй случай того же класса после
стёртого force-push'ем коммита, поэтому правило вынесено в `docs/MAINTENANCE.md`
отдельным пунктом: сборочная машина — потребитель репозиториев, а не место
для их редактирования.

Попутно: `git push` со сборочной машины по https виснет на запросе учётных
данных в неинтерактивной сессии — не падает с ошибкой, а именно висит до
таймаута. Ещё одна причина не редактировать там ничего.

Отдельная заметка про себя: `git push -q ... | tail && echo "запушено"` напечатал
«запушено» при отказе доступа — код возврата конвейера берётся от `tail`, а не от
`git`. Проверять результат надо по состоянию (`git rev-list --count`), а не по
тому, что команда «прошла».

## 0. Принцип, из-за которого форк iX сгнил, а наш не должен

iX вели `truenas/os` **merge-моделью**: сливали `releng/13.x` в свою ветку. За годы это дало
129 коммитов и 424 файла «дельты», в которой невозможно отличить свои патчи от вендорных
подтягиваний. Перенос на новый мажор превращался в проект.

Мы ведём **rebase-модель**: наш патч-сет — короткая серия коммитов поверх апстримного тега.
Подъём базы = `git rebase --onto`. Референс есть — у dravanet поверх `releng/15.0` ровно
**6 патчей и 12 файлов**:

| патч | файлы | нужен ли нам |
|---|---|---|
| `pmbr-datadisk` (protective MBR для дисков данных) | stand/i386/* | да |
| `force_depends` в rc.d/mountd, rc.d/nfsd | libexec/rc/rc.d/* | да |
| Remove excessive devd dependencies | libexec/rc/rc.d/devd | да |
| sysctl для generation непривилегированным | sys/kern/kern_priv.c | да |
| `ctld: change configuration live` | usr.sbin/ctld/* | да (главная фича dravanet) |
| `ctld:` возврат из inner main loop на EINTR | usr.sbin/ctld/ctld.cc | да |

Всё остальное, что было у iX (ixnvdimm, CTL/isp, bhyve/vncserver, EFI-serial, utimensat birthtime),
либо ушло в апстрим, либо нужно только HA-железу iX. Правило форка: **любой патч, который может
жить в апстриме, отправляем в апстрим и выкидываем из серии.**

## 1. Версии FreeBSD: не поэтапно

Поэтапный проход 13.3 → 13.5 → 14.0 → … → 15.x **не нужен и вреден**. `truenas/os` — форк
`freebsd-src`, вся история FreeBSD там уже есть; «переход на 15» — это наложить 6 патчей на
другой апстримный тег. Пошаговый проход даёт те же конфликты, только разрешённые N раз.

Поэтапность имеет смысл ровно в одном месте — **runtime-апгрейд боевых машин**, и там это тоже
не `freebsd-update`: TrueNAS ставит обновление новым ZFS boot environment целиком, поэтому
скачок 13.3 → 15.x одним апдейтом технически валиден. Ограничения по шагам — не в ядре, а в:
миграциях конфиг-БД middleware, feature flags пула (необратимо) и совместимости jail'ов.

**Рекомендация: `stable/15`.** Поддержка до 31.12.2029, security/errata прилетают в ветку сами
(отдельный процесс патчей не нужен), и следующие 15.1/15.2/… приходят тем же merge — это ровно
то, что нужно для «поддерживать все новые выходящие версии». Релизы форка резать по апстримным
`releng/15.x`-тегам.

Поправка по фактам: **15.2 ещё не вышла**. Актуальны: `releng/15.1` (15.1-RELEASE от 16.06.2026,
EOL 31.03.2027), `stable/15` (EOL 31.12.2029), `releng/15.0` (EOL 30.09.2026 — то, на чём стоит
dravanet), `stable/14` (EOL 30.11.2028). То есть после старта первым же делом поднимаем базу
с 15.0 на 15.1/stable/15.

## 2. Юридический контур: что чистить

Основная масса middleware — **LGPL-3.0** (файл `LICENSE` в репозитории). Форк абсолютно легален
при сохранении лицензии. Претензия iX к zVault была **не про логотипы, а про код**, явно вынесенный
под `LICENSE.IX` (TrueNAS Enterprise EULA, запрет на derivative works).

Файлов с пометкой `LICENSE.IX` в 13.3 — **46**:

| каталог | файлов |
|---|---|
| `src/freenas/usr/local/lib/middlewared_truenas/plugins/failover_` | 11 |
| `src/freenas/usr/local/lib/middlewared_truenas/alert/source` | 11 |
| `src/freenas/usr/local/lib/middlewared_truenas/plugins/enclosure_` | 9 |
| `src/middlewared/middlewared/plugins/kmip` | 6 |
| `src/freenas/usr/local/lib/middlewared_truenas/plugins` | 5 |
| `src/freenas/.../pytest/unit/...` | 4 |

Плюс не помеченные, но проприетарные по сути: `src/fenced/`, `sbin/hactl`, `firmware_update.py`,
`rc.d/ix-haready`, `alert/source/proactive_support.py`. Отдельно — торговая марка TrueNAS
(имя, логотипы в webui) и iX-овские ключи подписи обновлений.

**Что берём из zVault.** Их ветка `zvaultio/zvio-middleware:zvio-13.3` — это 30 коммитов
(154 файла, −10392 строки) готовой работы по вычистке, сделанной уже ПОСЛЕ претензии, то есть
согласованной с ней де-факто. Хронология подтверждает, что дело было в коде:

* 25.02.2025 `zvio init` — только ре-брендинг портов (`nas_ports/zvault/*`), первый релиз;
* релиз снят по претензии;
* 01.03.2025 `delete iX licensed files` — 41 файл, −7207 строк;
* март–май — `remove ha and kmip alert classes`, `remove kmip`, `stub failover`, `remove fenced`
  (заменён собственным портом `zvio-py-fenced`), `remove hactl`, `add rewritten sensor files`,
  `add function stubs`, `fix stub`;
* 04.05.2025 — второй релиз.

Тащить обратно то, что они удалили, нельзя — это ровно предмет претензии. Тащить **их чистку и
стабы** — можно и нужно: это их собственный код и готовая карта «что удалить, чем заменить».
zVault под FOSS-лицензией, при переносе сохраняем авторство коммитов.

**dravanet ничего не чистил** — в его дереве все 56 файлов проприетарной ветки на месте, README и
брендинг iX не тронуты. Для личного использования это не проблема; для публичного форка с ISO —
чистку надо делать самим (или переносить zVault'овскую).

## 3. Структура репозиториев

Свой GitHub org, репозитории — форки апстрима штатным механизмом (тогда GitHub сам считает
divergence и дружит с PR):

| репо | источник | ветки |
|---|---|---|
| `os` | форк `freebsd/freebsd-src` | `upstream/*` (зеркало), `patches/base` (наша серия), `base/15` (собранная база) |
| `middleware` | форк `truenas/middleware` | `main` (13.3-линия + наши), `vendor/dravanet`, `vendor/zvault` |
| `webui` | форк `truenas/webui` | `main` |
| `core-build` | форк `truenas/core-build` | `main` |
| `pkgtools` | форк `truenas/freenas-pkgtools` | `main` |
| `ports-overlay` | новый | только `nas_ports/` overlay; дерево портов — апстримное квартальное |

Дерево портов **не форкаем** — берём квартальную ветку `freebsd/freebsd-ports` (2026Q3) и кладём
сверху overlay. Это решение dravanet, и оно правильное: собственный форк ports был главным
источником гниения у iX.

## 4. Автоматизация трекинга (то, ради чего всё затевается)

**Сделано** — `tools/watch-upstream.sh` в `core-build`, еженедельно по cron на сборочной
машине (`0 9 * * 1`, лог в `~/upstream-watch.log`). Порядок работы описан в
`docs/MAINTENANCE.md`.

От исходного замысла отличается одним: наблюдатель **не заводит issue и не открывает PR**.
Авто-PR с переносом патч-сета означал бы, что машина решает за человека, где конфликт
разрешён правильно, — а именно на разрешении конфликтов проект уже один раз обжёгся.
Наблюдатель сообщает, решение принимает человек.

Второе отличие — журнал разобранного (`--ack`, файл `.upstream-seen`). Без него отчёт
показывает одно и то же каждую неделю и через месяц его перестают открывать; отчёт,
который не читают, хуже отсутствующего, потому что создаёт ощущение контроля.

Что показал первый прогон (2026-08-09):

| наблюдение | состояние |
|---|---|
| база FreeBSD | `stable/15` ушла вперёд от нашей точки — перенос назрел |
| бюллетени | 6 свежих EN, среди них `FreeBSD-EN-26:19.zfs` |
| порты | ветка `2026Q3` открыта, мы на `2026Q2` |
| OpenZFS | 2.4.3 — совпадает с собранным, действий не нужно |

Три из четырёх — реальная работа, которую теперь видно вместо того, чтобы узнать о ней
через год. Порядок действий по каждому сигналу — в `docs/MAINTENANCE.md`.

Исходный замысел (четыре наблюдателя):

1. **FreeBSD base** — новые коммиты в `stable/15`; раз в неделю пробный `rebase --onto`, при
   отсутствии конфликтов — авто-PR в `base/15`.
2. **Security Advisories** — лента FreeBSD SA/EN. При SA, затрагивающей нашу базу, — issue
   с меткой `security` и внеочередная сборка.
3. **Ports quarterly** — смена ветки 2026Q3 → Q4 (раз в квартал, ~1 числа второго месяца);
   авто-PR со сменой ветки в `repos.pyd` + прогон сборки.
4. **OpenZFS** — новые релизы `openzfs/zfs`; у dravanet для этого уже есть
   `tools/update_openzfs_ports.py` — переносим.

Плюс сборочный конвейер: self-hosted GitHub Actions runner на build-VM → `make release` →
артефакты (ISO + upgrade-tar) в GitHub Releases.

## 5. Доставка обновлений

* Разово — manual update tar через GUI. Шага подписи в `core-build` нет, файл применяется как есть.
* Постоянно — свой update train: `freenas-pkgtools` + сервер манифестов на своей инфре.
  Цели `update-push`/`release-push` в `Makefile.inc1` заточены под `update-master.tn.ixsystems.net`,
  заменяем на своё. Клиент переключается сменой train.

## 6. Порядок работ

**Этап 0 — инфраструктура (можно начинать сразу)**
1. Создать GitHub org, сделать форки, залить зеркала.
2. Поднять FreeBSD build-VM на Proxmox (16 ГБ RAM, 120 ГБ диск), self-hosted runner.
3. Прогнать первую сборку от dravanet **как есть**, на releng/15.0 — получить заведомо рабочую
   точку отсчёта, до всяких наших изменений.

**Этап 1 — свой контур**
4. Вынести патч-сет базы в `patches/base`, поднять базу 15.0 → stable/15, пересобрать.
5. Перенести чистку zVault, убрать брендинг iX, свой ре-брендинг.
6. Свой update train, первая публичная сборка.

**Этап 2 — трекинг**
7. Четыре наблюдателя из §4, CI на каждый PR.
8. Регламент релизов (например, ежеквартально по ротации ports + внеочередные по SA).

**Этап 3 — OCI**
9. См. §7.

## 7. OCI-контейнеры

Это самая приятная часть новости: **делать почти нечего на уровне ОС**. В FreeBSD 15.0 поддержка
OCI-контейнеров доведена до зрелого состояния: `ocijail` (OCI-runtime поверх jail, автор Doug
Rabson) + podman + buildah + CNI, тестовая программа FreeBSD OCI Runtime Extension Working Group
пройдена, ZFS-storage-driver признан основным и наиболее надёжным. То есть если база форка —
FreeBSD 15, рантайм у нас уже есть из портов.

Работа ложится не на ядро, а на middleware и UI:

* порты `sysutils/podman`, `sysutils/ocijail`, buildah, CNI-плагины — в `packages.pyd`;
* ZFS-датасет под storage podman + интеграция с pool-менеджментом middleware;
* плагин middlewared: `container.*` API (pull/run/stop/logs/volumes/networks) поверх podman;
* раздел UI (можно смотреть на то, как это сделано в SCALE/Goldeye — но там Linux и k3s,
  переиспользуется только UX, не код);
* сеть: bridge/CNI поверх существующей сетевой модели TrueNAS.

Логично делать после этапа 2 и **не раньше**, чем трекинг апстрима заработает автоматически —
иначе получим ровно ту же ловушку, в которую попал iX: новая функциональность есть, а база гниёт.

## 8. Открытые вопросы

* Имя GitHub org и имя продукта (нужно для ре-брендинга).
* Параметры build-VM и на каком Proxmox-узле.
* `stable/15` или `stable/14` как база — рекомендация в §1, решение за вами.
* Проверить на сборке: сохранилась ли в FreeBSD 15 совместимость для jail'ов со старым
  userland (актуально для миграции существующих iocage-jail'ов с 13.3).
* Судьба iocage: индекс плагинов iX мёртв; свой индекс (как `zvaultio/iocage-plugin-index`)
  или переход на bastille.
