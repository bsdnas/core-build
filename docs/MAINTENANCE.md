# Сопровождение форка

Форк живёт ровно до тех пор, пока за апстримом кто-то следит. Разрыв между
TrueNAS CORE 13.3 и FreeBSD 15, который пришлось разгребать в начале проекта,
возник не из-за сложной технической проблемы — просто год никто не переносил
патчи. Этот документ о том, чтобы история не повторилась.

## Наблюдатель

```
tools/watch-upstream.sh              отчёт в терминал
tools/watch-upstream.sh --quiet      молчать, когда нового нет (для расписания)
tools/watch-upstream.sh --ack        отметить текущее состояние разобранным
```

Коды возврата: `0` — нового нет, `10` — есть о чём доложить, `1` — ошибка.

Наблюдатель ничего не меняет и не открывает PR. Он сообщает — решение
принимает человек. Разобранное отмечается через `--ack` и попадает в
`.upstream-seen` (файл локальный, в репозиторий не входит). Без этого отчёт
всегда «красный», а такой отчёт перестают читать через месяц.

Запуск по расписанию, раз в неделю:

```
0 9 * * 1 cd /usr/build && tools/watch-upstream.sh --quiet
```

## Что делать по каждому сигналу

### База FreeBSD сдвинулась

Наш патч-сет лежит поверх `stable/15` в `bsdnas/os`, ветка `base/stable-15`.
Модель — перенос (rebase), а не слияние: именно накопленные слияния сделали
исходное дерево CORE неподъёмным.

```
git fetch up                                    # freebsd/freebsd-src
git rebase --onto up/stable/15 <прежняя-база> base/stable-15
```

Конфликты разбирать руками, коммит за коммитом. **Не «решать» конфликты
фильтрацией по регулярным выражениям** — однажды это оставило в дереве обе
стороны конфликта, и сборка упала гораздо позже и совсем в другом месте.

После переноса — полная сборка и `tools/acceptance.sh install`, иначе смысла в
переносе нет.

### Вышел бюллетень безопасности

Бюллетени FreeBSD (`SA` — безопасность, `EN` — errata) применяются к
`stable/15` апстримом, поэтому обычно достаточно обычного переноса патч-сета.
Отдельное внимание нужно, когда затронуто то, что мы патчили сами: ZFS, ядро,
загрузчик.

Проверить, дошло ли исправление до нашей ветки, можно по дате коммита в
`stable/15` относительно даты бюллетеня.

### Открылась следующая квартальная ветка портов

Ветка портов задаётся в `build/profiles/freenas/repos.pyd`. Смена квартала —
это смена версий сотен пакетов разом, поэтому менять её нужно **только вместе
с полной пересборкой и приёмкой**, а не «заодно» с другой правкой.

Полезно помнить: порты исчезают. `archivers/pxz` уехал из дерева, дистрибутивы
`arcconf`, `megacli`, `tw_cli` пропали и у вендоров, и в `distcache.FreeBSD.org`.
При смене квартала сборка может упасть именно так — это не поломка сборочной
системы.

### Вышел новый OpenZFS

В middleware есть готовый помощник:

```
tools/update_openzfs_ports.py <версия> <sha тега>
```

Версия порта — это тег релиза без префикса `zfs-` (релиз `zfs-2.4.3` →
`PORTVERSION= 2.4.3`).

Обновление OpenZFS — самое рискованное из четырёх: оно затрагивает формат
данных на дисках. Приёмка обязательно должна включать импорт пула, созданного
предыдущей версией.

## Место на сборочной машине

```
tools/prune-builds.sh            показать, что будет удалено
tools/prune-builds.sh --apply    удалить, оставив последние 3 сборки
```

Каждый `make release` оставляет каталог примерно на 1.3 ГБ в `_BE/release`
плюс образ рядом с объектным каталогом, и ничто их не удаляет.

Об этом стоит помнить, потому что переполнение раздела не выглядит как
переполнение. Один раз оно проявилось так: сборка шла 4 часа 50 минут и упала
сразу на семи портах — `rust` после 3 часов 39 минут, `grub2-efi`, `lsof`,
сборка Angular с `NG6002` в primeng и так далее. Каждое падение выглядело
самостоятельной поломкой; настоящая причина была одна — `ENOSPC`, и видна она
была только в `dmesg` (`filesystem full on /`) да одной строкой в глубине лога
Angular.

Правило: перед длинной сборкой смотреть `df -h /`. Меньше 40 ГБ свободного —
сначала уборка. Порог не абстрактный: одному только `rust` нужен рабочий
каталог в десяток гигабайт, а собирается он последним и три с половиной часа.

Размер диска сборочной машины: **320 ГБ**. Со 120 ГБ, с которых проект
начинался, работать нельзя — их хватает ровно на одну сборку без запаса.
Расширять можно на ходу, сборку прерывать не требуется:

```
qm disk resize <vmid> scsi0 +200G          # на гипервизоре
camcontrol reprobe da0                     # в гостевой системе
gpart recover da0 ; gpart resize -i 5 da0
growfs -y /dev/gpt/rootfs
```

`growfs` работает на смонтированном корне — это не требует ни размонтирования,
ни перезагрузки.

## Как правильно прерывать сборку

Убить `make release` на середине мало: poudriere монтирует дерево исходников
внутрь своего джейла через nullfs, и монтирование переживает смерть процесса.
Следующая сборка падает через минуту на попытке очистить каталог:

```
rm: .../objs/jail/usr/src/...: Read-only file system
==> ERROR: Build failed
```

Ошибка выглядит как поломка сборки, хотя это остаток предыдущего запуска.
Поэтому после принудительной остановки:

```
mount | grep /usr/build/freenas/_BE/objs      # посмотреть, что осталось
umount /usr/build/freenas/_BE/objs/jail/usr/src
jls                                           # джейлы poudriere не должны висеть
```

и только потом запускать заново.

## Не править скрипт, который сейчас выполняется

Bash читает скрипт по мере выполнения, по смещениям в файле. Правка на ходу
сдвигает смещения, и оболочка продолжает читать с неверного места:

```
tools/acceptance.sh: line 255: syntax error near unexpected token `|'
```

Файл при этом синтаксически цел — `bash -n` проходит. Поймано на живой
приёмке: вердикт был вынесен до того, как выполнение дошло до испорченного
места, но с тем же успехом прогон мог оборваться на середине и дать ложный
результат.

Правило: длинную приёмку править только после её завершения — либо на копии.

## Проверки перед коммитом

```
tools/check-sh.sh                    # синтаксис shell-скриптов (в middleware)
tools/acceptance.sh install <iso>    # чистая установка
tools/acceptance.sh upgrade <iso>    # обновление поверх работающей системы
```

## Правило про источник правды

Правки вносятся **в одном месте** и разъезжаются через GitHub. Сборочная
машина — потребитель репозиториев, а не место для их редактирования: правка,
сделанная там, однажды была стёрта force-push'ем и потерялась.
